abacus

A C++ decoder for Qwen2.5-0.5B that I wrote from scratch, and what I found when I compared it with llama.cpp.

Question

Generating text one token at a time is usually limited by memory: every new token reads all of the model’s weights. I wanted to know how close a small engine written from scratch could get to that limit on a laptop CPU, and how it would compare with llama.cpp, the standard tool for the job.

The first version answered that on my laptop. In the second version I changed the weight format and the kernels. I checked that the new format stays at least as close to the full-precision model as llama.cpp’s Q8_0, and then timed both engines on a cloud CPU. The baseline notes describe each comparison separately: the cloud run I did, the stricter laptop run I haven’t done, and the first version.

First version, on my laptop

The first version is a complete C++ forward pass for Qwen2.5-0.5B-Instruct: memory-mapped weights quantized to int8 with one scale per output row, a 32-bit key-value cache, and matrix-vector kernels in scalar, 256-bit and 512-bit SIMD code. The SIMD kernels widen the int8 weights and multiply them in 32-bit floating point. Without quantization it matches Hugging Face Transformers to within 0.00044 on every logit checked, and all 32 greedy tokens agree. The ceiling divides the measured read bandwidth, 39 to 43 GB/s depending on thread count, by the bytes each token has to read: about 500 MB of weights plus the cache. llama.cpp ran at a pinned commit with Q8_0 weights, its closest 8-bit format, at the same thread counts. Each point is the median of three runs of 16 tokens.

First version results

At short context the engine gets close to the ceiling. With 2 threads and 128 tokens of context it decodes 69.0 tokens per second, 83% of the ceiling, against 61.8 for llama.cpp. That is its best case: at 4 threads the two are level, and at 1 and 6 threads llama.cpp is faster. Long context is where the engine loses. At 4,096 tokens llama.cpp decodes 44.1 tokens per second and the engine 31.7, because its attention is still scalar code, which takes 17.2 of the 31.6 milliseconds per token.

Speed isn’t the whole comparison. The engine’s quantizer reads 5.5% fewer bytes than Q8_0, 8.03 against 8.50 bits per weight, but it distorts the output more: its mean KL divergence from the full-precision model is 0.029 nats against Q8_0’s 0.0097, although it matched the full-precision top token slightly more often, at 57 of 60 positions against 56. llama.cpp also ran with its default 16-bit cache and fused attention, both of which favor it.

Most of the speed came from vectorizing. The 256-bit SIMD kernels were 5.2 times faster than scalar code, and going to 512 bits added 10%. Switching from 16-bit to 8-bit weights changed scalar speed by only 1%. Every method slowed sharply at 12 threads, which is twice the laptop’s six physical cores.

Second version: weight format and quality

The second version stores int8 weights in groups of 64, each group with a 16-bit scale: 8.25 bits per weight against Q8_0’s 8.50, and a 509.73 MB file against 531.07 MB. I chose this format among four candidates on calibration text from Frankenstein, before scoring anything on the held-out text from Pride and Prejudice. The format had to beat Q8_0 on mean KL, 99th-percentile KL and top-1 agreement, and the smallest file that did was picked. Activations can stay in 32-bit floats, or be quantized to 16-bit integers so the matrix products run on AVX-512 VNNI integer instructions.

Each activation path had to pass its own quality rule before it could enter a final timing. With 8-bit activations, the rule required mean KL, 99th-percentile KL, top-1 agreement and perplexity all to be at least as good as Q8_0. That path failed, so it is left out of the comparisons below. With 16-bit activations, mean KL and 99th-percentile KL had to be lower than Q8_0’s and top-1 agreement higher, on both the calibration and the held-out text. Perplexity was reported but not required. That path passed. On 2,048 held-out positions with a 16-bit cache:

So my format is closer to the full-precision model by KL and top-1, but its perplexity is slightly worse. These are agreement measures, not task accuracy. The 16-bit decision records every report it used.

Second version: speed on one cloud CPU

I timed the 16-bit path against llama.cpp Q8_0 on one rented virtual machine. Its CPU reported family 25, model 17, which AMD documents as a Zen 4 EPYC; the model name itself was hidden. It exposed 24 virtual CPUs, which may not be dedicated physical cores. Both engines were compiled on that machine, used a 16-bit cache and the same CPUs, and greedily decoded 128 tokens per sample. I fixed the six cells in advance: 1, 2 and 4 threads at 128 and 4,096 tokens of context. Each cell has sixteen paired samples taken in an ABBA order. For llama.cpp, a short pilot in each cell picked its faster flash-attention setting, and those pilot runs are not counted. My engine held its CPU binding for the whole worker’s life, which is not how the laptop command line runs. The engine columns are median tokens per second; the ratio is my engine’s speed over llama.cpp’s.

My engine was faster in all six cells, by a median paired ratio of 1.090 to 1.531, and every interval is above 1. Each interval comes from resampling the ABBA quartets 20,000 times. They hold for each cell separately, not for all six at once, and the paired ratio is not the ratio of the two medians shown. An earlier run with 32-bit activations on a different cloud machine finished only 2 of its 6 cells and lost both, at 0.4108 and 0.3079. Because the machines differ, I can’t say how much of the change came from the VNNI instructions. The estimated cost of all cloud attempts, failures included, was $1.6074, an estimate rather than an invoice. Sources: summary, raw samples, earlier attempt and cost.

Laptop comparison I haven’t run yet

The code for a stricter laptop comparison is ready but I haven’t run it. It covers 1, 2, 4, 6 and 12 threads at three context lengths. In each cell it tries nine llama.cpp configurations and compares my engine with the fastest one. Until I run it, I make no laptop speed claim for the second version.

Exact lookup and a smaller cache

I also added prompt lookup, which guesses upcoming tokens from earlier text and checks them in one batched pass. On twelve prompts it produced the same 768 tokens as plain greedy decoding. It accepted 263 of 944 guesses: 53.9% on prompts that copy text and 6.7% on open-ended ones, 27.9% overall. Accepted guesses don’t prove a speedup, and I haven’t measured one. Lookup results.

An 8-bit cache that subtracts a fixed per-head key mean takes 27.54 MB at 4,096 tokens against 50.33 MB for the 16-bit cache, 45.3% less. On 64 held-out positions near 2,000 and 4,000 tokens its mean KL is 0.005105, against 0.000855 for the 16-bit cache and 0.030889 for a plain 8-bit cache. It is still numerically worse than 16 bits. The mean comes from the first 64 keys, which are kept at full precision, and that warm-up is mixed into the comparison. The 16-bit cache stays the default. Cache results.

Limits

Everything here uses one model. The first version ran on one laptop, with clock speeds and temperatures not fixed. Its ceiling is an estimate from a read benchmark, not a measured DRAM utilization. Its quality was checked on four short prompts, and agreement at long context wasn’t tested for it. The second version’s timing comes from one cloud machine whose load, clocks and memory layout I couldn’t control, and I have no read ceiling for that machine. None of this measures task accuracy or batched serving.
