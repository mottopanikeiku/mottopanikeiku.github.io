HeliosTune

Does tuning data from other GPUs make kernel tuning faster on a new one?

Question

Autotuning a Triton matrix-multiply kernel means timing many configurations on the target GPU. If timings from other GPUs predict which configurations are good, a new GPU should need fewer of them. HeliosTune tests that on an H100, using timings from L4, A10 and T4 GPUs.

Method

For each new matrix shape, a retrieval step finds the most similar shapes measured on the other GPUs, and a Bayesian linear Thompson sampler decides which configuration to time next on the H100. The combined policy, which I called Parhelion, spends its first probe on the retrieved recommendation and adapts from there. The study covers 96 shapes from four model families, 36 curated Triton configurations and 41,472 timing measurements across the four GPUs. Test shapes and their model families were held out of the retrieval archive.

Result

Transfer didn’t help. The selected transfer weight was zero, and plain cold-start Thompson sampling did slightly better over the first eight probes, with a mean score of 0.958 against 0.950.

Retrieval gave Parhelion a better first probe, but cold-start search overtook it on the second.

The bigger finding is the reference itself. torch.matmul, which is outside the 36 configurations, scored 1.61 on the same scale, 61% faster than the best curated Triton kernel. The search policy wasn’t the bottleneck; the set of kernels it searched was.

Limits

One fixed set of shapes and timing runs; the intervals cover policy seeds, not repeated hardware runs. A later engineering run on an H200 used different rules and isn’t pooled with these numbers.
